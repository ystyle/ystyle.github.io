<p align="center"><strong>仓颉生态创新开发挑战赛 · 复盘</strong></p>

<p align="center"><em>把官方评分表当成一面镜子</em></p>

> 官方公示名单我读了三遍。第一遍找自己，第二遍数别人，第三遍才去翻赛事规则里的评分表——那张表能解释的东西比名单多。

## 先说结果

仓颉生态创新开发挑战赛，2026 年 8 月 21 日启动，10 月 24 日线上决赛，11 月 10 日公示名单。

**238 人报名，200 支队伍参赛，41 件作品进决赛，60 个获奖名额，总奖金池 7 万。**

我投的是 **cjreg**——用仓颉实现私有中心仓与多仓体系，走的是「技术课题」赛道。拿的是**优秀奖，第 7 位**。

各档名额加起来：一等 1 + 二等 2 + 三等 5 = 8。所以 41 支决赛队伍里，**我排第 15**。

200 支里前 15，按分位算进了 7.5%。但离前三等差了 7 个身位。

看完评分表之后，这个位置是能算出来的。

两个加分项：

## 用这张表解释 60 个项目

我按类型把 60 个获奖项目归了一遍：

| 类型 | 数量 | 最高档位 |
| --- | --- | --- |
| **移植类**（把别的语言已有的库搬到仓颉） | 约 26 个 | 三等奖（colorama4cj） |
| **编译器 / 工具链** | 8 个 | 一等奖 / 二等奖 |
| **Agent / AI** | 6 个 | 三等奖（AgentSkills-runtime） |
| **基础设施**（数据库、协议栈、私有仓） | 6 个 | 三等奖（端侧向量数据库） |
| **应用 / 框架 / GUI** | 6 个 | 三等奖 |
| **验证 / 质量工具** | 4 个 | 一等奖（CangVer） |
| 计算 / 算法 | 4 个 | 三等奖（CJReduce） |

三件事能从评分表里读出来。

### 一、移植类占近一半，卡在「创新性」上

`orderedmap4cj`、`indexmap4cj`、`regex4cj`、`chrono4cj`、`threeten4cj`、`stats24cj`、`snakeyaml4cj`、`semver4cj`、`serde4cj`、`quickxml4cj`、`lz4cj`、`dataframe4cj`、`priorityqueue4cj`、`segmenttree4cj`、`fraction4cj`、`viper4cj`、`notify4cj`、`governor4cj`、`mdurl4cj`、`md54cj`、`thumbnail4cj`、`noise-rs`、`chrono_tz`……

26 个左右，接近一半。但档位最高的只有 `colorama4cj`（三等奖），其余都在优秀奖及以下。

对着评分表就说得通了：

- **创新性 20 分**要的是「方案是否新颖」。把这些库搬过来，接口是现成的，实现路径有参照——这一项很难拿高分
- **实用性 20 分**里有一条「**填补生态空白的作品适当加分**」。这条救了它们

所以移植类普遍落在「实用性给分、创新性丢分」的中段。这是评分规则决定的，不是搬得不好。

`colorama4cj` 能进三等奖，大概是代码质量和文档这两块拉满了——终端着色的接口不复杂，30 分的代码质量项容易做透。

### 二、前几等被「生态里没有替代品」的项目占了

- **一等奖 CangVer**——验证器
- **二等奖 第三方开源仓颉编译器及工具链**——自己实现编译器
- **二等奖 combinatorics4cj**——组合数学库
- **三等奖 性能优化（二进制体积和冷启动）**、**端侧向量数据库**

对照评分表：这类项目在**创新性 20 分**上天然接近满分（生态里没有），**实用性 20 分**上「填补空白」的加分也稳拿。两项加起来 40 分，比移植类的「实用性满分 + 创新性中段」多出一截。

编译器尤其典型。仓颉官方有编译器，「第三方独立实现」意味着语言规范被两套代码独立验证过——这是可信度层面的东西，不是功能层面。评分表里「创新性」考的就是这个。

### 三、Agent 类只拿到一个三等奖

Agent / AI 相关的有 `AgentSkills-runtime`（三等奖）、`鲁班（Luban）`（优秀奖）、`cjh`（入围）、`仓颉 AI 自动开发助手`（创新实践奖）、`语义驱动的跨语言库迁移 Skill`（入围）、`CangjieCompute`（入围）。

**最高只到三等奖，名额 1 个。**

原因大概率不在「评委不认 Agent」，在决赛那 30 分的「**核心功能演示**」：

> 作品能否现场正常运行；核心功能是否完整；**演示效果是否与提交材料一致**

编译器能跑测试用例、性能优化能出基准数字、向量数据库能压测。Agent 能演示，但「它到底好不好用」需要时间验证，现场很难说服人——评委只能看你当场跑出来的东西。

## cjreg 是干什么的

既然写到这里，把项目说清楚。

### 解决什么问题

`cjpm` 从中心仓装包。如果团队要发内部包，或者机器在内网没法出网，就得有个自己的仓。

cjreg 就是这个东西——一个可以自己部署的仓颉包仓库：

```
cjreg init
cjreg serve
cjreg admin
```

`init` 建库、建首个管理员、挂上官方上游；`serve` 起 HTTP 服务；`admin` 处理用户和仓库同步。

起来之后有门户（包列表、搜索）和管理后台（用户、权限、审计）。

### 几个实现上的决定

**多仓而不是单仓。** 配置里挂多个仓库，各带优先级。查包时按优先级找，找到就停。这样「官方仓 + 团队内部仓」可以并存，内部包能覆盖同名官方包。

**依赖解析自己做。** 版本约束、冲突检测、强制替换——这些不能甩给 cjpm，否则私有仓和官方仓的行为会不一致。

**三级删除。** 包、版本、文件三层分别可删，删之前检查引用。仓库最怕误删，删了别人就构建不过。

**审计日志。** 谁在什么时候发了什么、删了什么，都留痕。

### 实测数据

单机 loopback 冒烟基准，桩上游隔离（不用真实中心仓，避免网络抖动污染数据）：

| 维度 | 结果 |
| --- | --- |
| 索引：回源 → 本地命中 | p50 **16.16 ms → 2.74 ms（5.9×）** |
| 发布吞吐 | 2 MiB 74 MiB/s；32 MiB 278 MiB/s；200 MiB **324 MiB/s** |
| 发布内存 | 三档 VmHWM **恒定 291 MiB**（与包体无关，流式发布） |
| 并发（索引命中态） | 1/4/16/64 VU → 88 / 294 / **414** / 356 req/s（拐点 16–64 之间） |
| 启动 → 可服务 | **0.27 s** |
| SIGTERM 关闭 | 0.03 s（exit 0） |

### 重写时踩的五个兼容性坑

因为有 Go 版 cjrepo 做对照，这些坑是「照着 cjpm 的真实行为去适配」时才暴露的：

1. 官方索引的 `index-version` 是**字符串** `"1"`，不是数字。按 `Int64` 读会抛异常，整行解析失败
2. cjpm 的 `meta-data.json` 是 **pretty 多行 JSON**。按 NDJSON 逐行解析会失败，索引直接 404
3. cjpm meta 里的 `sha256sum` 和 `dependencies` 在**嵌套的 index 对象**里，读的时候要往下钻一层
4. bstorm（底层存储）重开需要 reindex；跨进程的 `nextId` 要恢复；`init` 必须 close 落盘
5. 用 `StringReader` 读二进制制品会报 UTF-8 错，得改成 `readStreamToBytes`

前三个是同一个教训：**别照着文档实现，照着真实产物实现**。文档写的是「应该是什么」，中心仓里躺的是「实际是什么」。

最后说一句名单之外的事。

那 26 个移植库，档位都不高。但仓颉要真被人用起来，缺的恰恰是这种「不好不坏、少了就难受」的东西——`indexmap4cj`、`priorityqueue4cj`、`fraction4cj`，每一个都在替生态填一个格子。

评委给的档位是给单个项目定的，生态的厚度是给这些东西累积出来的。两码事。
