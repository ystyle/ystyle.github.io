<p align="center"><strong>仓颉生态创新开发挑战赛 · 复盘</strong></p>

<p align="center"><em>41 支队伍进决赛，我排第 15</em></p>

> 官方公示的获奖名单我读了三遍。第一遍找自己，第二遍数别人，第三遍才看出来他们到底在挑什么。

## 先说结果

仓颉生态创新开发挑战赛，八月启动，十月决赛，11 月 10 日公示名单。

我投的是 **cjreg**——用仓颉实现私有中心仓与多仓体系。拿的是**优秀奖，第 7 位**。

把各档名额加起来：一等奖 1 + 二等奖 2 + 三等奖 5 = 8。所以 41 支进决赛的队伍里，**我排第 15**。

前 37%。不算差，但也没进前三等。

看到名单那一刻有点可惜。写完之后再看，这个位置是合理的——下面用数据说为什么。

## 60 个项目，分一下类

赛事一共 60 个获奖名额（41 支决赛队伍 + 19 支没能进决赛但单独设奖的）。按作品性质归类：

| 类型 | 数量 | 最高档位 |
| --- | --- | --- |
| **移植类**（把别的语言已有的库搬到仓颉） | 约 26 个 | 三等奖（colorama4cj） |
| **编译器 / 工具链** | 8 个 | **一等奖**（CangVer 算验证器，编译器工具链是二等奖） |
| **Agent / AI** | 6 个 | 三等奖（AgentSkills-runtime） |
| **基础设施**（数据库、协议栈、私有仓） | 6 个 | 三等奖（端侧向量数据库） |
| **应用 / 框架 / GUI** | 6 个 | 三等奖 |
| **验证 / 质量工具** | 4 个 | 一等奖（CangVer） |
| 计算 / 算法 | 4 个 | 三等奖（CJReduce） |

一眼能看到三件事。

### 一、移植类占了近一半，但拿不到高奖

`orderedmap4cj`、`indexmap4cj`、`regex4cj`、`chrono4cj`、`threeten4cj`、`stats24cj`、`snakeyaml4cj`、`semver4cj`、`serde4cj`、`quickxml4cj`、`lz4cj`、`dataframe4cj`、`priorityqueue4cj`、`segmenttree4cj`、`fraction4cj`、`viper4cj`、`notify4cj`、`governor4cj`、`mdurl4cj`、`md54cj`、`thumbnail4cj`、`noise-rs`、`chrono_tz`……

数下来 26 个左右，接近一半。

**但移植类里档位最高的只有 `colorama4cj`（三等奖）**。其余全在优秀奖及以下，甚至有好几个掉进「创新实践奖」和「决赛入围奖」。

这个信号很清楚：**补生态里缺的格子是有价值的，但评委不认为「搬过来」本身构成难度**——键值对、正则、时间库这些东西，接口是已知的，实现路径有参照，工作量集中在适配而不是设计。

### 二、前三等被「不能替代的东西」占了

看一等奖和二等奖：

- **CangVer**——验证器
- **第三方开源仓颉编译器及工具链**——自己实现编译器
- **combinatorics4cj**——组合数学库

三等奖里也有「性能优化：二进制体积和冷启动时间优化」「端侧向量数据库」。

共同点：**别人做不了，或者生态现在没有替代品**。

编译器尤其典型。仓颉官方有编译器，但「第三方独立实现」意味着语言规范被两个人独立验证过一遍——这是可信度层面的东西，不是功能层面的。

评委的原话也印证了这一点：

> 对三方库作品而言，能否持续维护、被他人真实调用，比一次评审得分更重要；对技术课题而言，能否沉淀为可复用的方案，才是对生态的实际增量。

「被他人真实调用」和「可复用的方案」——这是两个要求，不是夸奖。

### 三、Agent 类只拿到一个三等奖

名单里 Agent / AI 相关的有 `AgentSkills-runtime`（三等奖）、`鲁班（Luban）`（优秀奖）、`cjh`（入围）、`仓颉 AI 自动开发助手`（创新实践奖）、`语义驱动的跨语言库迁移 Skill`（入围）、`CangjieCompute`（入围）。

**最高只到三等奖，名额 1 个。**

这跟我原本的判断一致（我一度想投 Agent 方向，后来放弃了），但原因可能跟我想的不一样。

不是评委不认 Agent。是 Agent 类项目**很难当场验证**：编译器能跑测试用例，性能优化能出基准数字，向量数据库能压测——Agent 能演示，但“它到底好不好用”需要时间。

评委在两个多月里要看 41 个项目，只能看当场能复现的证据。

## 我的项目为什么是这个位置

cjreg 是「仓颉私有中心仓与多仓工具」——解决的是企业内网或团队内部要自己托管仓颉包的问题：多仓配置与优先级查找、依赖解析与版本冲突、私有仓一键部署、镜像与上游同步。

对照上面三条：

**稀缺性：中等。** 私有 registry 不是卡脖子的东西，官方中心仓能满足绝大多数人。它只在“内网不能出网”“团队要发内部包”这类场景里成为刚需。

**可验证性：中等偏低。** 要验证它，得先部署起来：跑 `cjreg init` 建库、`cjreg serve` 起服务、配 `cjpm.toml` 指向私有仓、发一个包、再从 zero 开始 pull 一次。**这条链路比“跑个基准”长得多**。

**反差：强。** 这一项我原本以为会是加分项——因为**我们之前用 Go 写过一版，叫 cjrepo**。同一个问题用另一门语言重做一遍，意味着需求被验证过两次，而且有对照基线。

但反差这一项，评审大概没时间看出来。41 个项目，每个都要看完材料，「这个项目有 Go 版前身」这种背景不写在标题里就容易被跳过。

**所以第 15 名，是「需求不够痛 + 验证成本太高」的结果，不是做得不够认真。**

## 顺便介绍一下 cjreg

既然写到这里，说清楚它是干什么的。

### 它解决什么问题

`cjpm` 从中心仓装包。如果团队要发内部包，或者机器在内网没法访问中心仓，就得有个自己的仓。

cjreg 就是这个东西——一个可以自己部署的仓颉包仓库：

```
cjreg init
cjreg serve
cjreg admin
```

`init` 建库、建首个管理员、挂上官方上游；`serve` 起 HTTP 服务；`admin` 处理用户和仓库同步。

起来之后有门户（包列表、搜索）和管理后台（用户、权限、审计）。

### 几个实现上的决定

**多仓而不是单仓。** 配置里可以挂多个仓库，每个有优先级。查包时按优先级找，找到就停。这样“官方仓 + 团队内部仓”可以并存，内部包覆盖同名官方包。

**依赖解析自己做。** 版本约束、冲突检测、强制替换——这些逻辑不能甩给 cjpm，否则私有仓和官方仓的行为会不一致。

**三级删除。** 包、版本、文件三个层级分别可删，但删之前会检查有没有被引用。仓库这种东西最怕误删，删了别人就构建不过了。

**审计日志。** 谁在什么时候发了什么包、删了什么版本，都留痕。内部仓往往给一个团队用，出了问题要能回溯。

### 部署

一个 Docker 镜像，数据全在挂载的 `/data` 目录（`cjreg.db` + `blobs/` + 配置）：

```bash
docker run -d -p 8060:8060 \
  -v /path/to/data:/data \
  ghcr.io/ystyle/cjreg
```

发大包（>30MB）时按机器内存调堆大小。

## 下次再报，我会先问三个问题

这次的经验能提炼成三个筛子，用来判断一个选题值不值得投：

| 筛子 | 具体问题 | cjreg 的得分 |
| --- | --- | --- |
| **稀缺性** | 生态里缺这个吗？已经有几家在做？ | 中（官方仓能兜底） |
| **可验证性** | 评委当场能怎么验？跑测试？出数字？看用户数？ | 低（要部署才能看） |
| **反差** | 有没有“别的语言已经这么干过”的对照？ | 强（有 Go 版 cjrepo） |

三个都高，前几等有戏。两个高，优秀奖。一个高，入围。

cjreg 是一个高两个中，第 15 名对得上。

**下次要做的不是“选个更难的题目”，而是“选个更好验证的题目”。** 难度评委看得出来，但如果验证成本太高，难度也白搭。

---

顺带说一句：获奖名单里那些我原以为“没什么意思”的移植库——`indexmap4cj`、`priorityqueue4cj`、`fraction4cj` 这些——虽然档位不高，但它们**占据了生态里最多、最基础的格子**。仓颉要真被人用起来，缺的正是这种“不好不坏、但少了就难受”的东西。

评委给的档位是给项目定的，生态的厚度是给这些东西定的。两码事。
