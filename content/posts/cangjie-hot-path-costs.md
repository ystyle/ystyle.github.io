写 tachyon（一个 fasthttp 风格的仓颉 HTTP 服务端）时，性能不是“优化”出来的，是**一笔一笔量出来、再一笔一笔砍掉**的。

这篇记五笔账：四笔要躲，一笔量完发现不存在。都不大，但每一笔都在每次请求里重复发生。所有数字都是在这台机器上跑出来的（AMD Ryzen 7 7840HS，仓颉 1.2.x）。

## 一、不开 `-O2`：55 倍

同一个逐字节扫描循环：

| 编译选项 | 吞吐 |
| --- | ---: |
| 默认 | 75 MB/s |
| `-O2` | **4189 MB/s** |

**cjpm 默认不开 `-O2`。** README 里得写上这一条，否则后面所有的性能设计都作废——你精心设计的零拷贝视图，编译器连内联都没做。

这不是“仓颉慢”，是所有 AOT 语言都这样。但它是**唯一一条“改一行配置、涨 55 倍”**的开销，所以排第一。

## 二、`String.fromUtf8`：1 MiB 要 544 µs

仓颉的 `String` 是带 UTF-8 校验的堆对象。构造一个 1 MiB 的 String，光校验就 544 µs。

热路径上这意味着：**每请求只要有几处“顺手转成 String”，CPU 就没了**。

tachyon 的做法是全程不转：解析 HTTP 时只记 `(start, len)` 两个下标，header 名比较用小写视图 + 索引对，body 从头到尾是指回读缓冲的视图。

只有在真正需要给用户一个 String 时才转——比如静态文件那个很少走的分支。

## 三、`Array<Byte>` 切片：27 ns，0 字节

这一条和上一条是配套的：既然不转 String，那就得靠切片。仓颉的 `Array` 切片是**别名**，不是深拷贝——实测每次 27 ns，堆分配 0 B。

这条我一开始判断错了：原以为是 `std.net` 的 `conn.read/write` 里造数组切片造成的。后来一量，切片根本不分配——**那条归因是错的**，作废。

真实的账在第四条。

## 四、socket 的 read / write：每次固定 56 字节

用裸 `TcpSocket` 单独量每次调用的分配：

| 操作 | 每次分配 |
| --- | ---: |
| 空循环（对照） | 0 B |
| 普通函数调用（对照） | 0 B |
| `write(80 B)` | **56 B** |
| `write(1024 B)` | **56 B** |
| `write` 传入切片 | **56 B** |
| `read(4096 B)` | 56 B |

两个结论：

1. **分配发生在 socket 内部，而且是常数**——写 80 字节和写 1024 字节一样多。所以它不是“数据拷贝的开销”，是每次调用固定的成本。
2. **和载荷无关，就没法靠“少传点数据”绕过去**，只能减少调用次数。

端到端对齐一下：裸 socket 做一个“accept → read → write 固定响应”的循环，每请求 **112 B**；tachyon 走完整 HTTP 流程（解析 + 序列化 + 读写），每请求也是 **112 B**。

也就是说：**tachyon 自己的 HTTP 层是 0 B/请求，整条链的分配量就等于 1 读 + 1 写两次 socket 调用的固定成本。**

这 112 B 是标准库的成本。想要再降，得让 `read`/`write` 接受复用缓冲的 API——那是 std 的事，不是应用层能解决的。

## 五、三个中间件：−9.6% QPS

给最小 handler 挂上 requestID + bodyLimit + CORS 三个中间件：

| | QPS |
| --- | ---: |
| 裸 handler | 594,443（今天量的） |
| 加 3 个中间件 | 约 −9.6%（仓库里 11-08 量的这组差） |

这 9.6% 是在 11-08 那组（约 562k 基线）上量的，不是 594,443 的 9.6%。

这 9.6% 花在哪，是能对应到代码的：**每请求多三轮闭包调用 + 三处 header 读写**。每一轮都要拿 ctx、读一个 header、写一个 header。

它不叫退化，叫真实代价。但值得知道：**中间件不是免费的**，一个“只是加个请求 ID”的中间件，实际是三个闭包调用和三处 header 读写。

## 这套数字是怎么量的

用的就一个函数：`std.runtime.getAllocatedHeapSize`。每次操作前后各取一次，差值就是这次操作的堆分配；跑两万次取平均。

三条纪律：

1. **必须有对照组。** 空循环、普通函数调用，量出来都必须是 0 B。对照组不为 0，说明取样方式本身在分配，那所有数字都不作数。
2. **端到端和逐调用分开量。** 逐调用回答“这笔钱在哪一层”，端到端回答“用户实际付了多少”。两者对不上，就是漏了某一层。
3. **看次数，不只看字节。** 同样 112 B，一次分配和一百次小分配对 GC 的压力完全不同。

第四节的表就是这么来的，脚本在 `bench/std-alloc-baseline`，跑一次就有。

## 什么时候不该绕

能绕的都在表里，但绕都有代价：

| 开销 | 绕法 | 代价 |
| --- | --- | --- |
| 不开 `-O2` | 打开它 | 编译变慢，二进制变大 |
| 构造 String | 全程 Bytes 视图 | 所有 API 都变成“自己处理字节” |
| socket 每次 56 B | 减少调用次数 | 只能批量，不能省单次 |
| 中间件开销 | 不挂 | 功能没了 |

表格里第二条最容易走偏：**为了 0 分配把所有东西都改成视图，代码会变得没法读。**

tachyon 的取舍是：热路径（解析、序列化、header 查找）全用视图；要给用户用的 API 照常返回 String。**热路径之外多分配一点无所谓，那是给人读的代码。**

## 一条实操顺序

如果只记一条：

> 先 `-O2`，再量分配，最后才谈“零拷贝”。

因为前两件是**有确定收益的测量**，第三件是**相信某个设计**。顺序反了，很容易花两周写零拷贝，结果 `-O2` 没开。
